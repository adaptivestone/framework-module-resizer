# 0.4.0: operating the module and adopting it on real data

Status: decided by the controller on 2026-11-04, after a review by three independent seats (Opus, Sol,
Astra). The owner asked for the release to be built without scoping questions ("work as much as possible
to solve all issues"), so every open choice below is a ruling, listed with what it costs if it is wrong.
The owner can overturn any of them in review.

## Why this release

0.3.0 passed its first trial on a real host's code: database queue, local storage, one entity (avatars),
all checklist items green, no finding that blocks adoption. The queue, the gate, freshness and the API
shape held up. What cost time was everything around them:

- a failed task does not say why in any log;
- a damaged upload becomes a gray preview, and the task reports success;
- a projection without the module's fields silently empties a listing;
- local storage does not work out of the box in a framework app;
- nothing tells a host with an existing image library what to do.

So 0.4.0 makes the module easy to run and easy to adopt, then finishes what 0.3.0 deferred: the image
engine port and push delivery.

## Goals

1. An operator can find out why a task failed from the logs alone, and a pipeline filtered at `error`
   hears about a dead task.
2. Silently wrong output stops: damaged sources fail visibly, and silent misconfigurations warn once.
3. `retryable` means what the docs say: `false` when no retry can help.
4. A host with existing media can adopt it in place, one entity at a time, without re-uploading it.
5. A new adopter gets working local storage from the scaffold, and reads only what a new adopter needs.
6. Host steps see only pixels, and the engine is replaceable by a host.
7. A task can run in an SQS-triggered Lambda with the same lease, retries, dead-letters and gate.

## Non-goals

- Changing the queue, the gate, freshness signatures or the read path's shape. The trial gave no reason to.
- Migration tooling. The module ships no migration and no reader of old record shapes; the host owns the
  loop and the write. `adoptOriginal` measures one object and returns a value; it writes nothing.
- Deleting storage objects. It stays the host's job.
- Geometry changes for small sources. The current rule is pinned by tests and is not signed into rows, so
  changing it would leave old rows counted as fresh at the old size.
- A Sharp-free install. Sharp stays a dependency in 0.4.0.
- FIFO queues, a public transport-neutral push API, a Lambda scaffold flag, per-variant persistence.
- A pace limit on regeneration waves, and `Resizer.close()`.

## Anti-goals: this release failed if

- a pipeline without steps writes different files, or stored previews regenerate on upgrade;
- pull workers get weaker or slower to serve push delivery;
- a read becomes able to throw or to run Sharp;
- good photos stop getting previews because the module became strict about harmless defects;
- a public document names a private reference project.

## Constraints

- Breaking changes are allowed (0.x), with no shims and no legacy readers. Each one is named in the changelog.
- A new error code joins `RESIZE_ERROR_CODES`, and an API change updates README, `AGENTS.md`, the changelog
  and the docs site's `docs/12-resize.md` in the same phase.
- The whole gate stays green at every commit: `npm test`, `npm run check`, `npm run types:check`, and
  `npm run build` and `npm run smoke` at the end of a phase.
- Nothing here can run against real S3, SQS or Lambda. Those checks are the owner's, listed under "Owner's checks".

### Adoption (phase B)

| # | Ruling | If wrong |
|---|---|---|
| B1 | **Adopting an existing object in place is supported.** New `hasOriginal(media)` and `resizer.adoptOriginal({ storageRef })`: it downloads and measures through the decoders and returns the same `Original` that `uploadOriginal` returns for that object. It writes nothing and queues nothing. No driver contract change. A hand-written bare ref stays allowed for bulk work: the worker measures it and backfills its dimensions, and a refusal then shows up as a dead task | A slightly larger API, additive |
| B2 | `adoptOriginal` refuses what a worker could never render, plus a public SVG, so it always runs the A4 decode: it already holds the bytes, and a damaged object that adopted cleanly would cost a download, a decode and an `error` line per cooldown for good. It does not apply `upload.maxBytes` or `upload.formats`, which are policy of an upload endpoint | About 0.1 s per 24 MP JPEG at attach time |
| B2a | **New `limits.sourceBytes`**, default 256 MiB. Blessing existing objects removes the protection `upload.maxBytes` gave workers: a bare ref to a 3 GB video would otherwise OOM-kill a worker on every delivery, taking other work down with it. `download(ref, { maxBytes })` gains an optional argument: the S3 driver checks `ContentLength` and the local driver `stat` before reading. The core checks the length afterwards too, for drivers that ignore the argument. Over the limit: `RESIZE_SOURCE_TOO_LARGE`, `false`. Not in `encodeSig` | A host with larger originals raises one number |
| B3 | **The S3 driver reads any key except control characters, `.` or `..` parts, a leading `/` or an empty part.** One reference host stores keys that hold the client's file name, so a strict alphabet would refuse a real library. Module-generated keys and `namespace` stay strict. `publicUrl` encodes each part. The local driver stays strict, because its keys are filesystem paths | A wider read gate, still limited to the two configured buckets |
| B4 | The two-bucket allowlist stays. A ref from client input is the real danger (it would publish previews of someone else's object), so the docs say to build refs from the host's own records | Hosts with a third bucket copy objects, or point `bucketPrivate` at it |
| B5 | The scaffold writes an explicit `privateRootDir`, an absolute `publicBaseUrl` from an environment variable, and new "Next" text, and appends `/var/` to `.gitignore` only in the run that writes the config. A private root inside a served parent cannot be detected, so there is no refusal, only the rule stated plainly. `rootDir: ''` and `privateRootDir: ''` are refused. The guide gains "Serve local files": a framework `bootHttp` recipe for development, tested, and proxy snippets for production, marked untested | A scaffold that edits a host's `.gitignore`, append-only like the `AGENTS.md` pointer |
| B6 | `formatPictureUrls` entries gain `width` and `height` when the row has them, since a size key does not promise a size. The real rule becomes a table in the guide | Two new JSON fields in hosts' API responses |
| B7 | The S3 driver imports the presigner only inside `signedUrl`. `RESIZE_PEER_MISSING` keeps its meaning | A missing presigner shows at the call rather than at `verify()` |
| B8 | A host decoder's originals are private unless the decoder sets `publicOriginals: true`. `SharpDecoder` sets it; the SVG check and its code stay | A host decoder with public uploads adds one line |
| B9 | Removed as promised: the deprecated `Framework*` storage types and the S3 driver's `publicUrl` option. The option throws `RESIZE_CONFIG_REMOVED_KEY` at construction, because a JavaScript host would otherwise fall through silently to bucket URLs, and a CDN-only bucket would then return 403 for every image | A clear error with an obvious fix |
| B10 | The testing recipe stays a recipe in the guide; no test helper ships | A second host copying it reopens this |
| B11 | Phase B's guide work: "Adopting on an app with existing media" (with: freeze the ref, because a changed ref regenerates; decide `limits.sourcePixels` before rollout, because raising it later makes every WebP and GIF row stale), namespace privacy and stability, the sizes table, read cost for hot lists, and the empty-`sizes` window. These ship with the code they describe, not in phase F | None |

### Core (phase C)

| # | Ruling | If wrong |
|---|---|---|
| C1 | After the worker's reload it looks at the rows read back under each `storageRef` it wrote. No such row (replica lag): nothing is raised. Rows exist, but none matches what was written in `identity`, `origin`, `encodeSig`, `sizeKey` and `format`: the task dead-letters with `RESIZE_MEDIA_ROW_NOT_KEPT`, naming the fields. Matching against the whole group matters, because a content-addressed store can return one ref for two rows with equal bytes (two size keys of a small source). This replaces the earlier idea of judging coverage from the reload alone, which would fail good tasks on a lagging reload | A store that "worked" by re-rendering on every read starts dead-lettering, which is the point |
| C2 | The Mongo dimension backfill writes only while the stored pair is absent, so it cannot land on a swapped original. Two dimension-less originals swapped during one render stays open | A rare wrong pair in a case that needs two hand-written originals |

### Engine (phase D)

| # | Ruling | If wrong |
|---|---|---|
| D1 | `VariantStep` becomes `(raster, { variant, ctx, media, source }) => Raster`, the same form as `beforeSteps`. Breaking. Measured: at task level the cost is inside the noise, and output is byte-identical in every compared case. Memory is the real cost, for steps only, and the README says so. No known host has a variant step today | Hosts rewrite one line per step |
| D2 | Each variant with steps gets its own copy of the pixels, so a step may write to it. Formats of one size share one raster, so without this an in-place step marks twice | 0.78 ms at 1920 wide, and the memory above |
| D3 | Flatten reads the channels of the step's result, which fixes black JPEG areas when a step adds transparency | A pipeline hit by this bug bumps its `version` |
| D4 | An old step that calls a Sharp method keeps the plain `TypeError`, with a troubleshooting row. A step that resolves with a Sharp instance gets a specific message | The wording of one error |
| D5 | Public `ImageEngine` port: `id`, `formats`, `animatedFormats`, `resize`, `encode`, optional `verify`. Passed in code as `engine`, like `decoders`; no config driver. Default `SharpEngine`, writing the same files as 0.3.0. The contract states that an engine must not write to its inputs, since formats of one size share one raster, and must be re-entrant, since calls run concurrently. A fake engine and a real non-Sharp library both fit the contract unchanged in the research | A contract with one real implementation today; it may still change in 0.x |
| D6 | Decoders stay separate from the engine, and `Raster` is their whole interface | A host wanting no Sharp at all waits for a later release |
| D7 | The engine is not signed into `encodeSig` and declares no version. Switching engines does not regenerate; bumping a pipeline's `version` does. `verify()` checks configured formats against `engine.formats`, and `SharpEngine.formats` lists the aliases Sharp accepts (`jpg`), because a host with `formats: ['jpg']` works today and renaming it would regenerate its previews | A custom engine must list what a host configures |
| D8 | `straightAlpha` becomes plain JS, up to 1 level different and slower, on rasters only a host decoder can mark, which keeps the contract at two methods | A third engine method |

### Push delivery (phase E)

| # | Ruling | If wrong |
|---|---|---|
| E1 | Narrow first version: standard SQS queues only, `createSqsHandler()` in a new `./lambda.js` entry, structural types, no new peer, no scaffold flag | A second transport needs its own design |
| E2 | `src/consumer.ts` does not change. A one-shot task queue runs each delivered record through the real `Consumer`, so pull cannot be weakened by code it does not see | Depends on three `run()` behaviours, which tests pin from both sides |
| E3 | Each delivery first sets the message's visibility to the lease ("adoption"), because on every receive it reverts to the queue's value, which is at least 6x the function timeout | Duplicate work only, if AWS behaves otherwise |
| E4 | A record that needs a retry is listed in `batchItemFailures`, never thrown, since a throw would slow all processing for one bad image. A trigger without `ReportBatchItemFailures` silently loses retries, which the handler cannot detect, so that setting comes first in the docs | Lost retries for a host that skips the documented setting |
| E5 | The remaining-time stop is load-bearing: rows persist once at the end of a task and preview keys are random, so a hard kill loses the attempt's work. The default reserve is `limits.processingTimeoutSeconds` + 5 s, never above half the time left; an explicit `stopBeforeTimeoutMs` is honoured as given. The reserve covers the whole end of a task: in-flight encodes and uploads, the persist and the queue calls, so the handler waits for the task to settle until 2 s before the deadline, then lists the record and returns. A record with too little time left is not started: it is listed, with an `error` line when that happens on the first record of an invocation, since that means the function timeout is too small | A task that always outruns the reserve burns its attempts and dead-letters visibly |
| E5a | The docs lead with the settings a host must get right: `ReportBatchItemFailures`, the IAM permissions the managed role lacks (`sqs:ChangeMessageVisibility`, and `sqs:SendMessage` on the dead-letter queue), `MaximumConcurrency` rather than low reserved concurrency, and `maxReceiveCount` = `maxAttempts` + 2 | None |
| E6 | Both host shapes use the same handler with no framework-specific code. The framework recipe is labelled as tried only on a minimal host until a real host has run it | Docs wording |
| E7 | **Ships marked "preview"** until the owner's AWS check passes: it is additive, and pull is untouched | Hosts wait for the mark to go, or the owner holds it for 0.4.1 |

## Delivery

Six stacked PRs on the module, each with its own plan, task reviews and a final review by Opus, Sol and
Astra: A signals, B adoption, C core, D engine, E push, F docs and release. One docs-site branch and PR
collects the guide changes, because the site should change only at release. The owner merges and publishes.
The version moves to `0.4.0` in phase F.

Phase A comes first because phases B to E rely on its logs and error classes. Phase F comes last because
every earlier phase edits the same documents.

## Owner's checks

Nothing below can run here. Each was left out of the build, not skipped silently.

1. **Real S3:** one adopted object, including a key with a space, through `adoptOriginal` and a worker.
2. **Real SQS:** a queued task through a worker.
3. **Real Lambda:** the push check list in `RELEASE.md`; the checks on retry delay and crash redelivery first.
   Until they pass, push delivery stays "preview".
4. **A count on real originals:** decode a sample at `failOn: 'error'` and `'warning'` and count refusals. If `'warning'` refuses about as few, it is the stricter default worth taking.
   `'warning'` refuses about as few, it is the stricter default worth taking.
5. **A frontend** handling the empty-`sizes` window, which needs a frontend.
6. **The npm name `resize-scaffold`:** free today, and the docs say `npx resize-scaffold`. Claiming it is cheap
   insurance against someone publishing there. Only the owner can do it.
