# 0.4 phase E: push delivery Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A queued task can run in an SQS-triggered Lambda with the same lease, retries, dead-letters and gate as a worker, through `createSqsHandler()` in a new `…/lambda.js` entry, marked "preview" until the owner's AWS check passes.

**Architecture:** Each delivered record runs through the real, unchanged `Consumer`, over a one-shot `TaskQueue` that hands out that one task and forwards every other call to the real `SqsTaskQueue`. The handler first sets the message's visibility to the lease, lowers `taskTimeoutMs` to the time it may spend, races the whole of `Consumer.run()` and the task's own promise against a deadline 2 s before the function timeout, and returns the records still in the queue in `batchItemFailures`. `runWorker`'s wiring moves into an internal `prepareServing()` that both paths use, so pull runs the same code as today.

**Tech Stack:** TypeScript with type stripping, `node:test`, Biome, `@aws-sdk/client-sqs` (existing optional peer, reached only through the driver), a fake SQS client in tests.

**Spec:** `docs/design/2026-11-04-0.4.0.md` (rulings E1 to E7 and E5a). Research: `.superpowers/sdd/2026-11-04-0.4.0/research/research-push.md` and `research/push-proto/`. The design overrules the research where they differ.

**Base:** branch `feat/0.4-e-push`, stacked on `feat/0.4-d-engine`. Phases A to D are in place: the `Consumer` logs failures itself (A1), `runWorker` logs one start line (A11), `ResizeConfigError` defaults to `retryable: false` (A5). Phase C's `onPreviewReplaced` fires from the shared render core, so a pushed task gets it with no code here. Line numbers rot, so this plan names functions and quotes anchors.

## Rulings

Each: what, why, cost if wrong.

1. **"Too little time" means `left - reserve < max(2000 ms, longest delivery so far)`.** So the default reserve refuses a first record under 4 s left, whatever `processingTimeoutSeconds` is, and an explicit one under `stopBeforeTimeoutMs + 2000`. The floor equals the settle margin. An explicit reserve is at least 3000 ms, so the stop comes at least 1 s before the handler stops waiting. Cost: a 2 s to 4 s function never runs a task, and a tail record with a slightly short budget uses a receive without partial progress.
2. **A record not started gets no visibility call: it is left alone and listed.** The `Consumer`'s give-back path still runs, so the gate is held for `gateTtlMs`, but `OneShotQueue.release` makes no queue call. Past `maxAttempts` it is dead-lettered unrun by the same path as before, only slower. With the settle deadline already passed, the handler makes no queue call and only lists it. Why: visibility 0 cost too much. Measured on the real handler in a model, not on AWS: at Lambda's default 3 s, every task was dead-lettered unrun within six deliveries as quick as Lambda could redeliver, and with no `deadLetterQueueUrl` the sixth delivery deleted it, so a backlog could die before anyone read the first line; above batch 1 healthy tasks died unrun (batch 10, 60 s function, 20 s tasks, 100 tasks: 34, 24 and 26 of 100 over three seeds). Leaving the visibility alone makes each receive cost a full visibility timeout, which is a window for an alarm and lets the queue drain before a tail record comes back. Cost: a tail record waits up to the queue's visibility timeout, against returning at once.
3. **The floor of the reserve.** An explicit reserve is at least 3000 ms — at exactly the margin the settle timer fires first, so the stop never lands (measured, 0 rows stored at return) — cost: a host cannot choose a reserve under 3 s, and a function of 4 to 6 s has under 1 s to finish. `createSqsHandler()` refuses a lower value with `RESIZE_CONFIG_INVALID`. The floor is `SETTLE_MARGIN_MS + 1000`, since a plain greater-than check would pass 2001, which also fails (0 rows stored). Above it there is no cap: it is honoured as given, even above half the time left.
4. **The margin is an internal seam.** `batchHandler(wiring, { settleMarginMs })` in `src/delivery.ts` is not exported from any entry; `createSqsHandler` passes `SETTLE_MARGIN_MS = 2000`. Tests use 300 ms, and two tests through the public entry pin the real 2 s. Cost: none in production.
5. **Adoption happens before the `Consumer` is built, not inside `claim`.** The research did it in `claim`. Outside, the budget can be computed after it, so a slow `ChangeMessageVisibility` comes out of the task's time and not out of the reserve. A record that will not start is not adopted. Cost: `resize.claim` no longer includes adoption, which nothing reads.
6. **Push methods live in an internal `DeliveryQueue` contract (`src/contracts/delivery.ts`), not on the public `TaskQueue` class.** The design rules out a public transport-neutral push API. `carriesSource(queue, source)` replaces the research's `queueOfSource(source)`, because a one-answer lookup would depend on the order of names when two names share a URL. A `DeliveryQueue` must have `release` and no `gatesByTask`, so the one-shot queue forwards no optional flags. Cost: a second transport moves a small interface.
7. **The wiring stays in `src/worker.ts` as `prepareServing({ pushed })`, not a new file.** The guards already treat `worker.ts` as the entry that looks Resizers up, and `worker.test.ts` passing untouched is the proof pull did not change. Cost: `worker.ts` stays long.
8. **Metrics flush once per invocation, waiting at most until half the margin before the deadline, never over 5 s.** Lambda gives no shutdown signal. Cost: `LogMetrics` writes one summary line per invocation.
9. **Checks that reject throw from the invocation, so no record is touched and the next invocation checks again. Checks still running at the settle deadline list every record, log `error` and return.** A rejected check is a setup error Lambda should back off from; a hung one must not reach the function timeout. No new code is needed. Cost: none known.
10. **The settle-deadline line is `warn`.** A retry follows, and a repeated failure reaches the `Consumer`'s dead-letter `error`, except for an adoption that does not answer: no `Consumer` ran, so nothing later reports it, and that line is `error`. Cost: an `error` filter does not hear about a one-off.
11. **An unknown event source is listed with an `error` line, not thrown.** No `eventSourceARN` is accepted only when exactly one queue is consumed. A throw would fail the batch for one miswired trigger. Cost: such a message loops until its redrive policy moves it, which the docs' `maxReceiveCount` bounds.
12. **The reserve reads `limits.processingTimeoutSeconds` of the task's own Resizer.** A task of an unserved Resizer has none, so its reserve is 5 s; it fails at once anyway. Cost: none.
13. **New codes:** `RESIZE_DELIVERY_UNSUPPORTED` (`ResizeSetupError`, default `retryable: true`, since a deploy can fix it) and `RESIZE_SQS_EVENT_INVALID` (`ResizeSetupError`, `retryable: false`). Neither ever fails a task, so neither joins the terminal-code list in `src/docsExports.test.ts`. Both join the `NOT_READ` list of phase A's `src/retryable.test.ts`, which must equal `RESIZE_ERROR_CODES` together with its other lists.
14. **The preview mark is one literal, `Push delivery (preview)`,** in the README heading and exports row, the guide heading, `AGENTS.md`, the changelog entry and the `src/lambda.ts` header, because "preview" alone means an image in this repository. `RELEASE.md` gives the `grep` that finds them. Cost: none.
15. **The README holds the reference and the guide holds the walkthrough, but both lead with the four settings of E5a.** That repeats four lines on purpose: a host who reads only one page must still not lose retries. Cost: four lines kept in step by hand.
16. **The framework recipe gets one test with a `FrameworkResizer` and the task queue passed in code, not a test of the recipe.** It proves E6's "no framework-specific code". The recipe itself stays labelled as tried only on a minimal host. Cost: the recipe can rot until the real-host trial.
17. **The redrive check.** No `maxReceiveCount` check on the first invocation — one SQS call per cold start for a setting real AWS has not been checked against — cost: a wrong value stays silent, so the docs and the owner's AWS check name it; decide after that check.

## Conflicts with the design

None. E5 says only that an explicit reserve is honoured as given, so ruling 3's floor conflicts with nothing. The end-of-task bounds can be met with `src/consumer.ts` unchanged, and this was run against the current file: the handler races `Consumer.run()` from outside, so an unbounded `tasks.fail`, a slow observer or a 30 s gate bound inside it cannot hold the invocation.

What stays, and is accepted: after the settle deadline the rest of the `Consumer` run goes on detached. If the environment is reused, it resumes in a later invocation, where it can fire a late `failed` event, set the visibility of an old receipt, and retake a released gate lock for at most backoff + lease (measured 64 s, Task 4's test pins it). All of that is duplicate work at worst. Changing the `Consumer` would not remove it, since a call already sent cannot be recalled.

- [ ] **Step 3: Implement the one-shot queue**

A private class `OneShotQueue extends TaskQueue` with a public `end: DeliveryEnd = 'left'`, built from `(carrier, task, stop: AbortController)`:
- `add` throws `new ResizeSetupError('resize lambda: a delivered task queue adds nothing')` (never called);

- [ ] **Step 4: Implement `batchHandler`**

Check the event first: `Records` an array, each record with a non-empty string `messageId`, and `context.getRemainingTimeInMillis` a function. Otherwise throw `new ResizeSetupError('resize lambda: the event is not an SQS batch: it needs a Records array whose records each have a messageId, and a context with getRemainingTimeInMillis() — check the function\'s trigger', { code: 'RESIZE_SQS_EVENT_INVALID', retryable: false })`. A record without a messageId cannot be listed, since Lambda reads an empty item identifier as a failure of the whole batch. A record with a `messageId` but a bad receipt, body or receive count is not thrown: it is listed alone with one `error` line naming it and makes no queue call, and its neighbours run. A throw would burn a receive on healthy neighbours each time, and repeated, they would die unrun past `maxAttempts`.

Then `ready ??= wiring().catch(forget and rethrow)`, then for each record in order, inside a `try` whose `catch` logs and ends `'left'`:

1. **Lane:** the first lane with `lane.carrier.carriesSource(lane.queue, arn)`, or, with no ARN, the only lane when there is exactly one. None: log, end `'left'`.
2. **Read:** `lane.carrier.taskOfDelivery({ id, receipt, body, receiveCount }, lane.queue)`. A string answer is the end.
3. **Adopt:** `await lane.carrier.renew(task, lane.deps.timing.leaseMs)`. `false`: log, end `'lease-lost'`. A throw: log once per handler, and run anyway.
4. **Run:** build `stop` and a `OneShotQueue`, and `new Consumer({ ...lane.deps, tasks: once, handle: wrapped })`, where `wrapped` calls `lane.deps.handle`, keeps `settled = running.catch(noop)` and returns `running`. Await `consumer.run(lane.queue, stop.signal)`, then `settled`. The end is `once.end`.

A record is listed unless it ended `'completed'`, `'dead'` or `'discarded'`. After the batch, `await wiring.flush(5000)` (Task 4 bounds it) and return `{ batchItemFailures }`.

- [ ] **Step 3: Implement the rules**

`defaultReserveMs` is `Math.min(processingSeconds * 1000 + 5000, Math.floor(remainingMs / 2))`. A private `settledWithin(promise, ms)` races `promise.then(() => true)` against a `setTimeout` of `Math.max(0, ms)` resolving `false`, always clearing the timer. It rethrows the promise's rejection.

The invocation, replacing Task 3's body after the event check:

```ts
const left = () => context.getRemainingTimeInMillis();
ready ??= wiring().catch((err) => { ready = undefined; throw err; });
let wired: DeliveryWiring | undefined;
await settledWithin(ready.then((w) => { wired = w; }), left() - margin);
if (!wired) {
  // A rejected check has already thrown. The wiring's logger does not exist yet.
  logNeverThrow(opts.logger ?? console, CHECKS_LATE);
  return { batchItemFailures: event.Records.map(({ messageId }) => ({ itemIdentifier: messageId })) };
}
```

Each record, in order. `index` is its place in `event.Records`, `longest` starts at 0, and `expired` starts false and turns true whenever a settle wait below runs out, so a later record of the batch never makes a queue call because a timer fired a millisecond early:

```ts
const lane = laneOf(wired.lanes, record.eventSourceARN);          // none: log, 'left'
if (expired || left() <= margin) { return notStarted(record, index, 0, margin); } // 'left', no queue call
const read = await settledRead(lane, record);                     // taskOfDelivery within left() - margin; late: expired, warn, 'left'
if (typeof read === 'string') { return read; }
const reserve = opts.stopBeforeTimeoutMs
  ?? defaultReserveMs(left(), (wired.processingSecondsOf(read) ?? 0));
const needed = Math.max(margin, longest);
const budget = () => left() - reserve;
if (budget() >= needed) {
  // renew within left() - margin. false: warn, 'lease-lost'. Late: expired, `error`, 'left'. A throw: log once, go on.
}
const start = budget() >= needed;
if (!start) { notStarted(record, index, Math.max(0, budget()), needed); }
const stop = new AbortController();
const once = new OneShotQueue(lane.carrier, read, stop, start);
let settled: Promise<unknown> = Promise.resolve();
const consumer = new Consumer({
  ...lane.deps,
  tasks: once,
  timing: { ...lane.deps.timing, taskTimeoutMs: Math.min(lane.deps.timing.taskTimeoutMs, Math.max(1, budget())) },
  handle: (t, o) => { const running = lane.deps.handle(t, o); settled = running.catch(noop); return running; },
});
const finished = consumer.run(lane.queue, stop.signal).then(() => settled).catch(logRunFailure);
const inTime = await settledWithin(finished, left() - margin);
if (!inTime) { expired = true; logNeverThrow(wired.logger, settleLate(`task ${read.taskId}`), undefined, 'warn'); }
if (start) { longest = Math.max(longest, performance.now() - startedAt); }
return once.end;
```

`OneShotQueue` gains a `start` argument: when false, the first `claim` aborts `stop` and still returns the task, so the `Consumer` dead-letters it past `maxAttempts` or else gives it back, and never runs it. `OneShotQueue.release` makes no queue call for such a task and resolves `false`, so the visibility stays as it is and the `Consumer` logs no `back in the queue` line. A record's `startedAt` is taken at its first line. `end` is read after the race: a `fail` still pending leaves `'left'`, and a `complete` the queue took stays `'completed'` however long an observer then takes.

After the batch: `await wired.flush(Math.max(0, left() - margin / 2))`.
