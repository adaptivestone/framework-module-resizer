# S6 — Hygiene and docs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the reference architecture. The test files are type-checked like the shipped code, new S3 previews carry a long-lived cache header, the README and AGENTS.md are guarded against the real exports, a fresh scaffold is proven clean against the published package, and the two older design docs say what replaced them. The release is `0.3.0-rc.5`; it adds no API a host must use and renames or removes nothing.

**Architecture:**
- **Test types.** One `tsconfig.tests.json` checks every `.ts` file under `src/` (tests and test helpers) plus the root tooling (`smokeTest.ts`, `preBuild.ts`, `postBuild.ts`, `bench/`). `types:check` runs it after the shipped-code check. The errors it reports today (92 here; one reviewer measured 91) are fixed in three batches without changing what any test asserts; each batch ends with zero errors in its files. Two of them are shipped typing bugs, fixed compatibly (D7). The two type-pin files (`contractShapes.ts`, `factoryTypes.ts`) keep their own small config, `tsconfig.type-pins.json`, which replaces `tsconfig.test-helpers.json` and still runs against the minimum peers in CI (`types:check:src`).
- **Cache header.** `S3Storage.upload` sets `CacheControl: 'public, max-age=31536000, immutable'` on every public object it uploads: previews, public raster originals, and a host's own direct uploads. Every key the module writes is new and random, so an object never changes under its URL; a host that calls the driver directly must give each upload a new key, as the `upload` contract already says. Private objects get no header.
- **Doc guards.** A test helper lists every entry of the package's `exports` map with its value and type exports and the declared name of its default export. A new test checks the README's "Package exports" section both ways (every export named, every name an export). It also parses every import form in README and AGENTS.md code fences and checks each against the exports (with negative fixtures), and checks that the README's list of codes a task is dead-lettered with at once matches the code.
- **Fresh scaffold.** The packaging smoke runs the published `resize-scaffold` bin three ways (default, `--eager`, `--eject`). Each output must pass `--check` and compile against the installed package.

**Tech Stack:** Node ≥ 24 (planned on 26.12.1), TypeScript 7 (`erasableSyntaxOnly`, `verbatimModuleSyntax`, ESM, `.ts` specifiers; strict by default), `node:test`, Biome 2.6, sharp 0.35, mongoose 9 and mongodb-memory-server (tests only), the framework 5.5 (dev).

**Spec:** docs/design/2026-10-26-reference-architecture.md. This plan covers:
- the S6 row of "Phases": "the rest of F10, superseded notes on the two older design docs, docs site";
- its "done when": "`npx resize-scaffold --check` clean on a fresh scaffold; README and AGENTS.md match the exports".

## Decisions

### D1. Version: `0.3.0-rc.5` (owner O1)

- **Recommendation:** `0.3.0-rc.5`. S6 completes the 0.3.0 scope, but rc.4 is not published and no real host has run S5's freshness check. S5's final review needed five fix rounds, each against a possible endless regeneration. RELEASE.md §5 (the real-host trial) is still a placeholder. The final `0.3.0` becomes a version bump after that trial, as RELEASE.md:49-50 already promises ("the final `0.3.0` is a bump from the last rc with no new heading").
- **Alternative:** `0.3.0` now. **Cost:** `latest` moves to code that no host has run, and the rc promise ends: any fix found in the trial becomes `0.3.1`.
- **rc promise kept:** S6 adds two widened types (D7; everything that compiled before still compiles) and a header on new S3 objects (D3). It renames and removes nothing. It changes no error code or text and leaves `src/signatures.ts` byte for byte (checked in Task 9).

### D2. No `processTask` export in 0.3.0 (owner O2)

- **Today:** `processTask(task, { signal })` (`src/worker.ts:48-54`) runs only the Processor. The task lifecycle is in the Consumer (`src/consumer.ts:279` `#runTask`, `:461` `#report`, `:503` `#finish`, `:664` `#releaseGate`): lease renewal, `complete`/`fail` with backoff, dead-letters, the gate lock and its owner, the cooldown, the task events and the metrics.
- **Why not export it:** a push host (an SQS-triggered Lambda) that calls it would skip that lifecycle. On SQS the gate lock `resize_gate:…` would stay held until `coordination.gateTtlMs` (10 min by default), so reads for that media would queue nothing. A failing task would never dead-letter through the module, never cool down, and fire no `onTaskDeadLettered`. A correct push API is a separate design: it must run the Consumer's lifecycle for one delivered message, with Lambda's partial-batch failure semantics and visibility-timeout renewal. It can come in a later release as an addition.
- **Alternative:** export `processTask` as it is. **Cost:** a public API that leaks gate locks, plus a signature frozen before the push design exists.
- **Docs:** README (Operations), AGENTS.md step 8 and the docs site each get one sentence: push delivery is not supported in 0.3.0, so run `runWorker` / `npm run cli ResizeWorker` in a long-lived process. Task 8 amends the F10 clause of the spec itself (`docs/design/2026-10-26-reference-architecture.md:234-235`, "`processTask` is exported for push-delivered tasks"): `processTask` stays internal in 0.3.0, and push delivery is planned for 0.4.0 (R-S6-2, R-S6-18).

### D3. The S3 cache header (owner O3)

- **Rule:** `S3Storage.upload` adds `CacheControl: 'public, max-age=31536000, immutable'` when `visibility === 'public'`. A private upload gets none. `ContentDisposition: 'attachment'` for SVG stays as it is (a private-only path today).
- **Why every public object, not only previews:** every key the module writes is new and random (128 random bits): `previews/<randomHex>.<ext>` (`src/processor.ts:1056`) and `originals/<randomHex>.<ext>` (`src/uploader.ts:198`). A replaced preview gets a new key, so no URL ever names changed bytes. The driver could tell previews apart by `parentRef`, but that is a placement hint, not a kind. The contract already says `upload` stores "a NEW object" (`src/contracts/storage.ts:19`).
- **Which objects:** every public object `S3Storage` uploads: previews, public raster originals (`uploadOriginal({ visibility: 'public' })` of a raster; a public SVG is refused), and a host's own direct `S3Storage.upload` calls. The driver does not enforce new keys (it sends a plain PUT), so the docs tell a host that calls it directly to supply a new key for every upload, per the contract.
- **What a host notices:** CDNs and browsers keep new public objects for up to a year. After the host deletes an object (it owns deletion), a CDN can keep serving its URL until purged; a random key does not help once the URL is known. Hosts that must make an image disappear quickly purge their CDN. This goes in README, AGENTS.md, CHANGELOG, host adoption and the docs site, with one wording: "every public object `S3Storage` uploads (previews and public raster originals, and a host's own direct uploads)" (R-S6-19).
- **`LocalFsStorage`** sets no headers (it writes files). The docs advise serving `rootDir` with a long-lived cache (for Express, `express.static(rootDir, { immutable: true, maxAge: '1y' })`).
- **Alternative:** a `cacheControl?: string | false` option on `S3StorageOptions` and the `storage` section. **Cost:** a new option, its validation in `S3Storage.fromConfig`, its type in `S3StorageConfig` and the docs. It can be added later as an addition if a host asks.

### D4. What "README and AGENTS.md match the exports" checks (owner O4)

The README is the reference, so it is checked both ways. AGENTS.md is a guide, so it is checked for stale names only.

- **README "Package exports" section** (`README.md:294-306`, rewritten in Task 5):
  1. One table row per key of `package.json` `exports`, `./package.json` included (its row says it is the package manifest), and no other row.
  2. Every value and type export of each code entry is named in backticks in its row. For the main entry, the row and the grouped list under the table count. An entry with a default export either names the default export's declared name in backticks (`export default class ResizeTaskModel` → `ResizeTaskModel`) or says "default export" in its row (R-S6-15).
  3. Every backticked identifier in a row (main entry: row and list) is an export of that entry, or the declared name of its default export. This catches renamed or removed names.
- **README and AGENTS.md code fences:** every import of `@adaptivestone/framework-module-resize…` in a code fence is parsed, in every form: single or double quotes; named, default, namespace (`* as X`) and side-effect (`import '…'`) imports, and their combinations; `import type {…}` and inline `type X` specifiers; `A as B` renames; imports that span lines (R-S6-16). Each names a known subpath (any key of the exports map, `./package.json` included), and every imported name is a real export of it: named values must be value exports, `type X` and `import type {…}` names must be type or value exports, and a default import needs a default export. Negative fixtures pin that the parser flags each bad form.
- **README and AGENTS.md text:** every `…/x.js` short path, and every quoted `'@adaptivestone/framework-module-resize/…'` specifier anywhere in the file (dynamic imports and prose included), is a key of the exports map.
- **AGENTS.md** need not name every export. The existing `src/agentsDoc.test.ts` stays as it is.
- **Where the export names come from:**
  - Values: the runtime module (`Object.keys(await import(entry))`).
  - Types: the entry's source. That is every `type` specifier of its `export {…} from` lists, every `export type {…} from` list, its own `export interface|type X`, and, for `export type * from './types.d.ts'`, every `export interface|type X` of that file.
  - The default export's declared name: `export default class|function X` in the entry's source (none for `export default <expression>`).
  - A sanity test checks that the parsed value names equal the runtime names, so the parser cannot drift unseen.
- **Alternative:** check values only (runtime keys). **Cost:** the 48 `types.d.ts` types and the contract types hosts write against (`MediaLike`, `ResolveOpts`, `TaskAddResult`, …) could be renamed or dropped from the README unseen.

### D6. How the test type errors are fixed

These rules bind Tasks 1–3.

1. **No assertion changes.** No `assert.*` call changes its expected value or message, no test is removed or renamed, and no test body changes what it exercises.
   - An added `assert.ok(x)` that narrows a value the test already uses as non-null is allowed. The test failed on that value before; now it fails one line earlier, with the same outcome. This is also how `command.test.ts:724` is fixed: an added `assert.ok(line !== undefined, out)` before the unchanged assert, whose message stays `line` (R-S6-20).
   - Reading the same value through a call, to undo a narrowing an earlier `assert.deepEqual(x, [])` made (`node:assert/strict` asserts `actual is T`), is allowed: the asserted value is the same array.
   - Splitting `assert.equal((await q.claim(…)).taskId, 'rh')` into a local, a narrowing `assert.ok`, and the same `assert.equal` on the local is allowed: same expected value, same message.
   - Moving a call under test into a typed helper that makes the same call (`verifyTasks(fixture.tasks)` for `fixture.tasks.verify()`, Task 3) is allowed when the matcher is unchanged.
2. **Order of preference:**
   1. correct types at the source (an explicit element type, `as const`, `satisfies`, a typed fixture, a generic tap);
   2. narrowing;
   3. a typed helper in `src/testHelpers/`;
   4. `// @ts-expect-error <reason>` on a line that deliberately passes a value the types forbid, as a JS host might (a media `original: {}`; numbers through a `resolveSizes` waterfall).
3. **Never:** `as any`, `@ts-ignore` or `@ts-nocheck`.
   - `as unknown as T` only inside a named helper in `src/testHelpers/`, with a one-line reason, or where the file already has it (`taskQueue.test.ts`'s `insert()`).
   - A Mongoose document passed as the Resizer's media uses the one-line cast hosts are told to write, `doc as MediaLike` (D8, R-S6-20); no helper.
   - An `any` only with a `biome-ignore` reason, as the house rule says, and only where a Mongoose generic cannot be expressed otherwise. The verified recipes below need none.
4. **Spreads of contract-typed fakes:** `{ ...memoryLocks(), verify }` is typed without the methods, because a spread of a class type drops its methods. Rewrite it as `Object.assign({}, memoryLocks(), { verify })`: the same own properties on a new object, so a fake that is used again later is not changed.
   - If a test only passes because a method is missing at runtime, stop and report.
5. **Shipped code changes** only as D7 lists. Any other shipped-type change a fix seems to need is a stop-and-report.
6. **Recipes.** Tasks 1–3 give, per error site, a recipe that was compiled against `f704e6e` with D5's config and the D7 changes (zero errors left in every listed file) and whose files' tests were run (PASS). Follow them; where your compiler reports a different set of errors, fix what it reports under these rules. Each task ends with zero errors in its files, not with a count.

### D8. A Mongoose document is not a `MediaLike` under strict types (owner O5)

- **Finding:** `src/drivers/mongo/frameworkFree.integration.test.ts:124`, `:198`, `:200`, `:208`, `:281`, `:348`. A hydrated document of a schema that spreads `resizeMediaSchemaFragment` is not assignable to `MediaLike`. Mongoose types the nested `original` as `{…} | null`, and its fields as `T | null`, while `Original` has none of those `null`s (`src/types.d.ts:51-58`, `:101-106`). A strict TypeScript host that writes `resizer.resolve({ media: await File.findById(id), sizes })` gets a type error. The runtime accepts it: a stored `null` dimension already counts as missing (`src/freshness.ts`, `storedDims`).
- **The design already says** "where Mongoose infers loosely the HOST layers `TsTypeOverride<Original>` / `TsTypeOverride<Preview[]>`" (`src/drivers/mongo/mediaFragment.ts:9-11`). Neither README nor AGENTS.md tells a host that.
- **Ruled (R-S6-7):** document the workaround in S6 and leave the types unchanged.
  - A plain `doc as MediaLike` compiles under strict types for a hydrated document and for `.lean()` of a schema that spreads `resizeMediaSchemaFragment` (a reviewer checked both against mongoose 9; the Task 3 recipes compile it for hydrated documents).
  - Tests write that same cast, `media: file as MediaLike`; there is no `asMediaLike` helper (R-S6-20).
  - The smoke's `CHECK_TYPES` pins the documented cast, next to `typedMediaStore` (Task 6), so the README and AGENTS.md advice cannot go stale.
  - README "Without the framework" and AGENTS.md step 6 each get one sentence: with strict types, pass the document as `MediaLike` (`import type { MediaLike }`), or type the model's `original`/`previews` paths with `Original`/`Preview` (framework hosts: `TsTypeOverride`).
  - Follow-up for a later rc or 0.4.0: a media input type for `resolve`/`prewarm`/`generate`/`invalidate` that accepts `null` fields and Mongoose arrays.
- **Alternative:** widen `Original`/`MediaLike` (and probably `Preview`) to accept `null` now. **Cost:** these types are also read by hosts, in `MediaStore.loadMedia` results, decisions and `GenerateResult.created`. The `previews` side, a `DocumentArray` of `T | null` fields, has not been measured, and a hygiene phase would ship a type design without its own review.
