# План: uploadOriginal() с сохранением SVG

Статус: реализован в ветке `codex-upload-original-queue-reliability`. Дата: 2026-09-17.
Итог: добавлены `Resizer.uploadOriginal`, `ResizeOriginalError`, upload-лимиты конфигурации,
байтовое определение растровых форматов и отдельный нерастеризующий SVG/XML-анализатор.
Ниже сохранён исходный план и критерии приёмки.
Контракт модуля: полученный SVG сохраняется как SVG без растеризации.
Полученный JPEG/PNG сохраняется в своём формате. Обработка файла до вызова API
находится за границами модуля; формат определяется по фактическому содержимому.
План универсален для приложений, использующих пакет.

отдельного плана или реализации `uploadOriginal` при проверке не обнаружено.

## Зачем

В модуле уже есть `ResizeStorage.upload()`: он получает готовые байты, ключ,
MIME и visibility, сохраняет объект и возвращает `StorageRef` (`key`, иногда
`bucket`). Распознавание изображения и сборка `Original` остаются у приложения.

Добавить общую операцию, чтобы приложения могли использовать единые правила
загрузки и метаданных. Это перенос повторяемой логики в пакет, а не обещание
ускорить worker. Интеграцию и миграцию каждое приложение планирует у себя.

## Реализованный контракт

```ts
const original = await resizer.uploadOriginal({
  body: buffer,
  visibility: 'private',
});
```

- `body`: непустой `Buffer | Uint8Array`.
- `visibility`: обязательное `public | private`; размещение определяет storage.
- Лимиты байтов, пикселей и разрешённых форматов задаёт конфигурация приложения
  при настройке модуля. Это не параметры, бесконтрольно приходящие от клиента.
- Результат совместим с существующим `Original`: `key`, необязательный `bucket`,
  определённые `format`, `contentType`, `size`; размеры — когда их можно
  достоверно определить. Существующий тип `Original` не делать строже для старых данных.
- Сохранять входные байты без скрытого перекодирования, поворота, удаления EXIF
  или схлопывания анимации. Любые будущие преобразования — отдельный контракт.
- Метаданные описывают сохранённые байты. Например, SVG имеет расширение `.svg`,
  `format: 'svg'`, `contentType: 'image/svg+xml'`, `size: body.byteLength`.
- Метод не создаёт Mongo-документ, не назначает владельца, не ставит задачу
  и не запускает генерацию превью. Ошибки явно выбрасываются через существующую
  иерархию `ResizeError` со стабильными кодами и причиной ошибки storage.

## Шаг 1. Распознавание и метаданные

Добавить внутренний helper подготовки описания original и публичный метод
в `src/resizer.ts`; экспортировать необходимые типы через `src/index.ts`.
Перед записью проверить лимиты и формат по содержимому, а не имени/MIME клиента.
Генерировать уникальный ключ с безопасным расширением из определённого формата.
Вызвать существующий storage.upload и объединить его locator с метаданными.
Не создавать второй S3-клиент или второй механизм записи файлов в этом методе.

Для SVG использовать разбор XML/SVG без рендеринга и загрузки внешних ресурсов.
Проверять корневой SVG-элемент, запрещать DTD/внешние сущности. Один regex по
расширению или строке `<svg` не является проверкой файла.
Не передавать SVG в Sharp для получения растрового результата.
Размеры SVG с процентами, относительными единицами и одним viewBox не выдавать
за известные пиксельные размеры: документировать правила, неизвестные опускать.

В AGENTS.md сейчас запрещён Sharp на request path. Выбрать ограниченное чтение
метаданных без декодирования/перекодирования пикселей; описать стоимость этой
проверки. Если реализация требует Sharp.metadata для растров, согласовать это
в контракте документации как ограниченное исключение, а не скрыто вводить
sharp(...).toBuffer(). Проверка заголовка не гарантирует полную декодируемость;
ошибка повреждённых пикселей может обнаружиться позже у worker.

## Шаг 2. SVG: хранение, безопасность и чтение

Существующий pass-through сохранить: SVG не ставится в resize-очередь,
worker не создаёт для него набор JPEG/WebP/AVIF. В разных размерах используется
доступный SVG-original; в ответе указывать его реальный MIME.

Санитизация SVG по текущему контракту принадлежит host. Приложение применяет
явную политику безопасного SVG до uploadOriginal: очистить опасное содержимое
с сохранением SVG либо отклонить неподдерживаемый/опасный файл. Санитизация
может изменить XML; модуль сохраняет без изменений именно переданные ему байты.
Не путать сохранение векторного формата с обещанием публиковать любой исходный XML.

Private SVG доступен через поддерживаемый драйвером авторизованный signed URL.
Не подставлять publicUrl приватного объекта при ошибке доступа. Публичный SVG
использует подтверждённый публичный locator. Политику доступа, публикацию и
собственные endpoint приложения модуль не определяет.

LocalFsStorage сейчас использует одно публично раздаваемое дерево и не обеспечивает
изоляцию private/public. Зафиксировать это как ограничение dev-драйвера;
проверку приватности проводить на S3 или реально защищённом storage/endpoint.

## Шаг 3. Тесты и документация пакета

- JPEG, PNG, WebP/AVIF из разрешённого набора: MIME, размер, locator, сохранение байтов.
- SVG с XML-декларацией, namespace, viewBox, относительными размерами: остаётся SVG;
  никакой растеризации, resize-задач или выдуманных размеров.
- Пустые/неподдерживаемые файлы, поддельный MIME, превышение лимитов, опасный XML:
  понятная ошибка до записи; отказ storage не возвращает успешный Original.
- EXIF-ориентация, прозрачность, анимация: исходник не меняется, поведение последующего
  worker проверено и описано.
- Local FS: чтение сохранённого файла совпадает с входом. S3: правильные bucket,
  Content-Type, public/private; не выдаётся публичный URL private SVG.
- Совместимость custom storage: достаточно действующего upload-контракта.
- README и AGENTS: реальный пример нового API, границы проверок, SVG pass-through,
  требования к sanitization и приватности. Существующие generate/prewarm не менять.

Проверки реализации: `npm test`, `npm run types:check`, `npm run check`,
`npm run build`; проверить экспорт и установку собранного пакета в host.
Выпустить новую версию пакета с документированным API и проверить её установку
в минимальном тестовом приложении без проектных моделей и legacy-адаптеров.

## Границы ответственности и готовность

Модуль получает байты и возвращает Original через настроенный storage. Он не
знает имён моделей приложения, маршрутов HTTP, владельцев, бизнес-сущностей,
формата DTO, социальных провайдеров и способов обработки изображений клиентом.
Приложение сохраняет Original в своей модели, определяет права и каталоги,
а затем при необходимости вызывает существующие generate/prewarm/resolve.

Готовность: публичный метод экспортирован и типизирован; SVG сохраняется SVG,
метаданные соответствуют байтам; отсутствуют скрытые преобразования; ошибки
явные; совместимость storage и прежнего Original сохранена. Проверены public
и private сценарии и отсутствие задач/растровых превью для SVG. Тесты, проверка
типов, lint и сборка проходят. Примеры документации используют только доступный API.

Подтверждение очереди и восстановление частичной генерации описаны в отдельном
[плане надёжности очереди](2026-09-17-queue-reliability.md). Это независимые
доработки модуля; uploadOriginal сам по себе их не исправляет.
Удаление объектов и управление жизненным циклом данных, миграции приложений —
отдельные задачи. uploadOriginal не расширяет MediaStore обязанностью создавать документы.
