# План: подтверждение постановки задач и полная генерация превью

Статус: реализован в ветке `codex-upload-original-queue-reliability`. Дата проверки: 2026-09-17.
Итог: добавлен `enqueueRequired` с явным покрытием/неполнотой и опциональным подтверждением
активных задач транспортом; worker завершает растровую задачу только при полном покрытии,
сохраняя частичные успехи для генерации только недостающих identities на повторе.
Ниже сохранён исходный анализ и критерии приёмки.

## Подтверждённое поведение

Проверены checkout `1390351` и локально известный `origin/main` `23402d2`.
На обоих сохраняются две описанные ниже ситуации. Upstream по сети в этой
проверке не обновлялся. Перед реализацией сверить актуальную базовую ветку.
На checkout выполнены существующие `src/prewarm.test.ts`, `src/enqueue.test.ts`,
`src/resizeTask.test.ts`; все три файла тестов прошли. Они проверяют нынешнее
поведение и не доказывают наличие предлагаемых новых гарантий.

### Q1. prewarm не позволяет подтвердить полную постановку запроса

`src/engine.ts:prewarmImpl` возвращает `{ enqueued: 0 }` для готового набора,
SVG pass-through, отсутствующего transport и перехваченной ошибки.
`src/enqueue.ts:enqueue` также возвращает 0 при проигранных dispatch-lock,
исключении transport и ответе `{ taskId: null }`. Ошибка получения lock отдельного
варианта приводит к его пропуску, даже когда другие варианты были поставлены.

Реальный сценарий: приложение один раз вызывает prewarm, transport недоступен,
получает 0 и продолжает работу. Если последующие чтения не ставят задачи,
автоматического повторения producer-операции нет: worker нечего обрабатывать.
Запуск worker или истечение lock сами по себе не создают отсутствующую задачу.

Другой сценарий: процесс A получил lock и остановился до enqueue. Процесс B
видит занятый lock, но сохранённой задачи ещё нет. Занятый lock не подтверждает
наличие задачи. Положительный enqueued тоже может отражать только часть запроса.

Текущий prewarm намеренно best-effort и never-throw. Для необязательного прогрева
это допустимо. Пробел — отсутствие отдельного API для приложений, которым нужно
подтверждение постановки всех требуемых вариантов или явный неполный результат.

### Q2. Worker считает частичный результат успешным

`src/resizeTask.ts:processTask` бросает ошибку только при
`generated.length === 0 && failedCount > 0`. Если один вариант сохранён,
а другой завершился ошибкой, обработчик возвращается нормально. Transport
трактует это как успех и не повторяет задачу из-за оставшегося варианта.
Тест `partial success (one good + one poison)` закрепляет именно такой результат.

Пример: запрошены JPEG и WebP; JPEG сохранён, WebP не удалось записать в storage.
Задача успешно завершается с одним готовым вариантом. Аналогичная неполнота
возможна при пропуске варианта из-за worker-lock: счётчик failedCount не растёт.

Это не повторная загрузка original и не ошибка SVG. Нужен явный контракт
завершения растровых задач и восстановления недостающих вариантов.

## Шаг 1. Добавить строгую операцию постановки

1. Оставить текущие resolve/prewarm совместимыми: read-path не начинает бросать
   исключения. Предлагаемое имя нового API — `enqueueRequired`; имя и тип
   утвердить в API-дизайне. Такой метод сейчас отсутствует.
2. Переиспользовать общие расчёты каталога, identity, filters, pipelines и hooks.
   Не дублировать их в приложениях. Зафиксировать набор после разрешённых hooks;
   исключённые политикой варианты и пустой запрос описывать явно, не как ready.
3. Результат описывает весь разрешённый набор: готовые варианты, подтверждённые
   постановки, неподтверждённые варианты. Различать ready, accepted, not-required
   (например SVG), incomplete и ошибки. При невозможности гарантировать постановку
   возвращать явную неполноту либо типизированную ошибку с частичным результатом.
4. accepted означает подтверждение transport для конкретного набора вариантов,
   а не завершение генерации. Возвращать доступные taskId и покрытие запроса;
   существующую задачу учитывать только при доказанном совпадении/покрытии.
5. Занятый lock не считать accepted. В случае гонки перечитать доступное состояние
   и/или выполнить ограниченную повторную попытку; без подтверждения оставить
   результат retryable/incomplete. Не вводить бесконечное ожидание в HTTP-запросе.
6. Сбой transport, null taskId, ошибка lock и отсутствие настройки должны быть
   наблюдаемы программно. Неоднозначный timeout не означает доказанное отсутствие
   задачи: возвращать неопределённость с безопасным путём повторения.
7. Согласовать контракт Mongo, SQS и custom transport. Mongo может подтвердить
   существующую активную задачу по requestKey; не требовать от SQS Mongo-подобного
   поиска. При нехватке возможности использовать совместимое расширение драйвера
   или явную ошибку capability. Документировать гарантии подтверждения каждого
   драйвера; не обещать exactly-once или одинаковую долговечность всех хранилищ.

## Шаг 2. Повторять недостающие варианты у worker

1. Для существующего растрового media успех задачи означает наличие всех
   запрошенных задачей identities в сохранённых previews после успешных uploads.
   Проверять фактическое покрытие, а не только generated.length/failedCount.
2. Сохранённые успешные варианты оставлять; недостающие после частичного сбоя
   переводить на существующий retry/backoff. Повтор обрабатывает только отсутствующие
   identities. Не создавать дубликаты превью и не переписывать готовые варианты.
3. При занятом worker-lock повторно проверить сохранённый результат конкурента.
   Если результат ещё отсутствует, задача остаётся неполной, а не completed.
4. Сохранить lease fencing, остановку по AbortSignal и освобождение собственных
   locks. После потери lease старый worker не должен подтверждать завершение.
5. Оставить конечный предел попыток и dead-letter для неустранимых сбоев;
   указывать, какие варианты не созданы. Логи/observer отражают partial/retry,
   а afterTaskComplete вызывается только после выполнения нового контракта.
6. Сохранить особые случаи: удалённый media — документированный no-op;
   существующий media без original.key — явная media-ошибка; случайная задача
   SVG — pass-through/no-op без растеризации. Отсутствие raster previews у SVG нормально.
7. Публичный eager generate сохраняет `{ created, failed }` и допускает частичный
   результат по своему контракту. Изменение worker не должно незаметно ломать этот API.

## Шаг 3. Проверки и выпуск

- Недоступный transport, null taskId, неоднозначный timeout: strict-операция не
  выдаёт ложный успех; существующий prewarm сохраняет совместимое поведение.
- Lock занят, но задачи нет; producer остановился между acquire и enqueue;
  часть locks недоступна; конкурент поставил тот же запрос: покрытие и статусы честные.
- Уже готовый набор, пустой/отфильтрованный набор и SVG различаются в результате.
- Частичная ошибка кодирования/upload, ошибка appendPreviews, занятый worker-lock:
  задача повторяется либо явно не завершена; успешные варианты сохраняются.
- После восстановления следующий запуск создаёт недостающее; постоянная ошибка
  достигает dead-letter. Удалённый media и SVG не попадают в цикл повторов.
- Потеря lease и повторная доставка не дают ложного completed и дубликатов.
- Проверить строгий сценарий на Mongo и SQS, ограничения custom transport и
  совместимость optional peers. Обновить тест partial success под новый контракт.

Запустить focused tests, затем npm test, npm run types:check, npm run check,
npm run build. Описать новое API, изменённую семантику worker и правила повторения
в README/AGENTS и release notes. Оценить влияние на существующих потребителей:
worker теперь может повторять задачи, которые раньше считались успешными.
